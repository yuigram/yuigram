# 20 — Бот-наблюдатель за статусом «в сети»

Оператор пишет боту имя пользователя, аккаунт рядом находит этого пользователя и наблюдает то,
что Telegram сообщает о его статусе, а бот пересказывает наблюдения оператору. Бот работает через
Bot API, аккаунт — через MTProto, оба живут в одном `App`, и все обращения к Telegram идут через
Yuigram.

| Файл | Что в нём |
| --- | --- |
| `watch.ts` | Вся логика: команды, модель наблюдения, опрос, уведомления |
| `index.ts` | Запуск с настоящим Telegram |
| `login.ts` | Однократный вход аккаунта, с вопросами в терминале |
| `keys.ts` | Однократная подготовка файла с публичными ключами серверов Telegram |
| `server-keys.ts` | Откуда берутся эти ключи и как проверяются |
| `rehearse.ts` | Репетиция без сети: подставные бот и аккаунт, сценарий статусов |
| `config.ts` | Чтение настроек и открытие клиентов и хранилищ |
| `.env.example` | Все имена настроек с безопасными заглушками |

Наблюдать можно только за теми, кто на это согласен.

## Что умеет бот

Команды принимаются только от оператора и только в его личном чате с ботом. Остальным бот
отвечает, что он закрыт, и к аккаунту не обращается.

| Команда | Действие |
| --- | --- |
| `/start`, `/help` | Список команд |
| `/watch @username` | Найти пользователя и начать наблюдение |
| `/unwatch @username` или `/unwatch id` | Прекратить наблюдение |
| `/list` | Кого наблюдаем и последнее наблюдение по каждому |
| `/status`, `/status @username` | Подробно: что известно, откуда и когда |

Наблюдение привязано к идентификатору пользователя, а не к имени: если имя сменится, наблюдаемый
останется тем же, а `/status` скажет, что имя изменилось. Группы, каналы, боты, несуществующие
имена и сам наблюдающий аккаунт отклоняются с объяснением.

## Репетиция без сети

```bash
pnpm tsx examples/20-presence-watch/rehearse.ts
```

Не нужны ни токен, ни вход, ни соединение. Бот и аккаунт — тестовые клиенты из `yuigram/testing`,
пользователи выдуманы, статусы идут по сценарию, часы и таймер подставные. Репетиция проверяет,
что сказал бот и о чём спросили аккаунт, и завершается с ошибкой на первом расхождении.
Настройки, ключи и состояние она держит во временном каталоге, который сама создаёт и удаляет;
настоящий `.env` она не читает и ничего не скачивает.

Чтобы увидеть сами сообщения бота рядом с проверками:

```bash
pnpm tsx examples/20-presence-watch/rehearse.ts --show
```

## Первый запуск: по шагам

Все команды выполняются из корня репозитория. Пример использует возможности, которых ещё нет в
опубликованном `yuigram@0.1.0`, поэтому запускается из рабочей копии.

### 1. Сборка

```bash
pnpm install
```

```bash
pnpm build
```

### 2. Публичные ключи серверов Telegram

```bash
pnpm tsx examples/20-presence-watch/keys.ts production
```

Для тестовой среды — `keys.ts test`. Среда называется всегда: умолчания нет.

По этим ключам аккаунт отличает серверы Telegram от любого другого, кто ответит по их адресу.
Поэтому файл должен происходить из источника самого Telegram, а не из ответа сервера и не из
случайной страницы. Telegram встраивает эти ключи в собственные клиенты, исходный код которых
публикует. Команда берёт один файл исходного кода Telegram Desktop — репозиторий
[telegramdesktop/tdesktop](https://github.com/telegramdesktop/tdesktop), на который ссылается
[telegram.org/apps](https://telegram.org/apps), — в зафиксированной ревизии
`90c89dcde9aec6974883fd1a270d4ee50d8ba688`:
`Telegram/SourceFiles/mtproto/mtproto_dc_options.cpp`. В нём ключи двух сред лежат в двух
таблицах: `kPublicRSAKeys` — боевая, `kTestPublicRSAKeys` — тестовая. Те же два ключа держит TDLib
(`td/telegram/net/PublicRsaKeySharedMain.cpp`, ветка `is_test`).

Команда проверяет, что полученный файл побайтно совпадает с проверенным (SHA-256
`64a50e0e1650c9313f36eefb16df245085f35718bbd84faa0d99ef9192b43111`), читает ключи разбором самого
Yuigram, сверяет отпечатки и пишет `examples/20-presence-watch/telegram-keys.production.pem` (для
тестовой среды — `telegram-keys.test.pem`). Отпечатки, которые она печатает:

| Среда | Отпечаток ключа |
| --- | --- |
| `production` | `d09d1d85de64fd85` |
| `test` | `b25898df208d2603` |

Существующий файл команда не перезаписывает: если в нём те же ключи, она так и говорит; если
другие — отказывает и оставляет файл как есть. Это единственная команда примера, которая
обращается куда-либо, кроме Telegram, и при обычном запуске ключи не скачиваются.

Если аккаунт при соединении сообщает, что датацентр предлагает ключ с другим отпечатком, не
добавляйте в файл ключ «под этот отпечаток»: проверьте `TELEGRAM_ENV` и адрес, а новые ключи
берите только из того же источника (как обновить зафиксированную ревизию, сказано в
`server-keys.ts`).

### 3. Настройки для входа

```bash
cp examples/20-presence-watch/.env.example examples/20-presence-watch/.env
```

Для входа нужны только настройки аккаунта:

| Имя | Что это | Откуда взять |
| --- | --- | --- |
| `TELEGRAM_ENV` | `production` или `test` — общая среда для бота и аккаунта | Выбираете вы; та же, что в шаге 2 |
| `API_ID`, `API_HASH` | Учётные данные приложения | [my.telegram.org](https://my.telegram.org), «API development tools» |
| `SERVER_KEYS` | Необязательно: другой PEM-файл с ключами | По умолчанию — файл из шага 2 для выбранной среды |
| `DC_ID`, `DC_HOST`, `DC_PORT` | Необязательно: первый адрес датацентра | По умолчанию — датацентр 2 выбранной среды |
| `DATA_DIR` | Необязательно: каталог состояния | По умолчанию `examples/20-presence-watch/state` |

`BOT_TOKEN` и `OPERATOR_ID` пока можно оставить заглушками: `login.ts` их не читает.

Файл `.env` читается из каталога примера, из какого бы каталога ни запускалась команда;
переменная, уже заданная в окружении, важнее файла. Относительные пути в `SERVER_KEYS` и
`DATA_DIR` отсчитываются от каталога примера. Файлы `.env`, `*.pem` и каталог состояния Git не
отслеживает.

### 4. Вход аккаунта

```bash
pnpm tsx examples/20-presence-watch/login.ts
```

Команда спрашивает в терминале номер телефона, код от Telegram и, если он есть, пароль
двухэтапной аутентификации (пароль не отображается). Вводятся они только здесь и никуда не
записываются. Авторизация сохраняется в `examples/20-presence-watch/state/account`. После входа
команда печатает имя и **id аккаунта**; при повторном запуске она ничего не спрашивает.

### 5. Оператор и бот

Впишите в `.env`:

| Имя | Что это | Откуда взять |
| --- | --- | --- |
| `OPERATOR_ID` | Числовой id единственного пользователя, чьи команды бот принимает | Id, который напечатал `login.ts`, если командовать будете с этого же аккаунта |
| `BOT_TOKEN` | Токен бота | @BotFather той же среды |
| `POLL_SECONDS`, `WATCH_LIMIT` | Необязательно: интервал опроса (не меньше 30 с) и предел наблюдаемых (не больше 20) | По умолчанию 60 и 10 |
| `TIME_ZONE` | Необязательно: часовой пояс для времени в сообщениях | Например `Europe/Moscow` |

Без `OPERATOR_ID` наблюдение не запускается: бота, который не знает своего оператора, пример не
поднимает. Если командовать будет другой аккаунт, сначала запустите пример со своим id и отправьте
боту с того аккаунта любую команду, например `/start`: бот ответит, что он закрыт, и назовёт
написавшему его id. Затем впишите этот id в `OPERATOR_ID` и перезапустите.

### 6. Запуск

```bash
pnpm tsx examples/20-presence-watch/index.ts
```

`index.ts` ничего не спрашивает: если аккаунт не вошёл, он сообщает об этом и завершается. Ошибка
в настройках называется одной строкой до любого соединения: какая переменная не задана, где
осталась заглушка из `.env.example`, какого файла нет.

### 7. Команды

В личном чате с ботом, с аккаунта оператора:

```
/watch @username
/status @username
/unwatch @username
```

`/watch` отвечает текущим статусом, дальше бот сам пишет о замеченных переходах. `/list`
показывает всех наблюдаемых.

### 8. Остановка

`Ctrl+C` в терминале, где работает `index.ts`: сначала останавливается наблюдение (таймер,
обработчики; чтение в пути дожидается ответа), затем клиенты. Второй `Ctrl+C` завершает процесс
немедленно. Список наблюдаемых сохраняется и при следующем запуске подхватывается сам.

**Остановка — не выход из аккаунта.** После `Ctrl+C` каталог `state/account` остаётся вошедшим
аккаунтом: следующий `index.ts` продолжит без вопросов, и любой, кто получит этот каталог, получит
доступ к аккаунту. Чтобы отозвать авторизацию, завершите этот сеанс в настройках Telegram
(«Устройства» → активные сеансы) и удалите `state/account`. Удаление каталога без завершения
сеанса авторизацию не отзывает.

## Среда и учётные данные

Бот и аккаунт всегда работают в одной среде: её задаёт одна переменная `TELEGRAM_ENV`. Каталог
состояния запоминает среду, для которой создан, и запуск с другой средой отклоняется — боевой бот
и тестовый аккаунт не имеют общих чатов. Для тестовой среды нужны её собственные бот, аккаунт и
ключи; файл ключей выбирается по `TELEGRAM_ENV`, поэтому ключи одной среды не подхватываются для
другой.

Токен, `API_HASH` и каталог `state/account` — учётные данные. Их нельзя публиковать, вставлять в
сообщения и журналы. Файл ключей не секретен, но от его происхождения зависит, кому аккаунт
поверит как серверу Telegram.

## Что где хранится

| Путь | Что в нём |
| --- | --- |
| `telegram-keys.<среда>.pem` | Публичные ключи серверов Telegram из шага 2 |
| `state/account/` | Авторизация аккаунта, его датацентры и известные ему пользователи. Это вошедший аккаунт |
| `state/watch/` | Список наблюдаемых, последние наблюдения, открытые интервалы и неотправленные уведомления |
| `state/environment` | Среда, для которой создан каталог |

Чтобы начать наблюдение заново, остановите пример и удалите `state/watch`.

## Как идёт наблюдение

- **Обновления.** Telegram сам решает, о чьих статусах присылать обновления аккаунту, и
  подписаться на произвольного пользователя нельзя. Пришедшее обновление обрабатывается сразу.
- **Опрос.** Раз в `POLL_SECONDS` аккаунт читает всех наблюдаемых одним запросом. Чтения не
  накладываются друг на друга; внеочередное чтение возможно не чаще раза в 30 секунд.
- **Порядок.** Ответ на чтение, запрошенное до того, как о пользователе стало известно что-то
  ещё (пришло обновление, или его сняли и поставили заново), к этому пользователю не применяется:
  решает следующее чтение. Остальные пользователи из того же ответа обрабатываются как обычно. Это
  порядок, в котором данные обработала сама программа, а не порядок событий в Telegram — его
  программа не знает. О порядке в Telegram говорят только его собственные отметки времени: время
  «был(а) в сети» не идёт назад, поэтому наблюдение с более ранним временем или статус «в сети»,
  истёкший до уже известного времени, считаются устаревшими и ничего не меняют.
- **Разрыв соединения.** Ответ на чтение, которое было в пути во время разрыва, отбрасывается:
  неизвестно, когда он был составлен. Читается заново.
- **Ограничения Telegram.** При `FLOOD_WAIT` чтение приостанавливается на указанное время, а
  следующие интервалы удлиняются.
- **Уведомления.** Состояние и уведомление записываются вместе, уведомление удаляется из очереди
  только после успешной отправки. После сбоя оно будет отправлено повторно, поэтому доставка —
  «не меньше одного раза»: дубль возможен, потеря — нет, пока отправка не отказала пять раз
  подряд.

## Чего пример не знает и не утверждает

- **Видно только то, что Telegram показывает этому аккаунту.** Если пользователь скрыл время
  захода, бот сообщает «точное время скрыто» и переходов не определяет.
- **Тишина не означает «не в сети».** Истёкший срок статуса «в сети» — повод прочитать ещё раз,
  а не переход.
- **Когда пользователь вошёл, Telegram не сообщает.** Статус «в сети» несёт только время, до
  которого он действует. Поэтому начало интервала — это момент, когда программа впервые увидела
  «в сети», а не момент входа.
- **Два наблюдения не доказывают, что между ними пользователь был в сети непрерывно.** И
  отсутствие сообщения «не в сети» этого не доказывает.
- **Если пользователь уже был в сети, когда началось наблюдение,** интервал не оценивается, даже
  когда известен конец.
- **Разрыв соединения, перезапуск, отказ чтения и `FLOOD_WAIT`** прерывают наблюдение интервала:
  он сообщается с причиной и без оценки. Интервалы через разрыв не склеиваются.
- **Короткие заходы между двумя чтениями** могут остаться незамеченными, если Telegram не
  прислал обновление. Сумма оценок — не «время в сети».

## Что означает каждое время и каждая длительность

| В сообщении | Что это | Чьи часы |
| --- | --- | --- |
| «замечено: …» | Когда программа узнала о статусе: обработала обновление или получила ответ на чтение. Не момент входа и не момент ухода | Этого компьютера |
| «статус действует до: …» | Срок, который Telegram дал статусу «в сети». Не начало и не конец пребывания: статус может быть продлён или снят раньше | Telegram |
| «был(а) в сети до: …» | Время последнего пребывания в сети, как его сообщает Telegram | Telegram |
| «последняя проверка: …» в `/status` | Когда о пользователе в последний раз узнали то, что относится к текущему моменту: ответ на чтение или обновление, изменившее состояние. Повтор обновления и устаревшее наблюдение проверкой не считаются | Этого компьютера |
| «первое наблюдение «в сети»: …» | Начало интервала в смысле примера: когда «в сети» увидели впервые после другого состояния | Этого компьютера |
| «оценка интервала: N» | Разность между «был(а) в сети до» и первым наблюдением «в сети». Это оценка, а не измерение и не граница: она верна, только если пользователь вошёл в момент первого наблюдения, не выходил до конца и часы компьютера и Telegram согласованы | Оба |
| «вход мог произойти раньше … тогда оценка — до M» | Та же разность, отсчитанная от предыдущей проверки, когда статус ещё не был «в сети». Вторая оценка при другом допущении о входе, а не гарантированный максимум | Оба |
| «это позже, чем сообщалось раньше …» | Telegram сообщил более позднее время «был(а) в сети», а входа программа не видела. Заход был, длительность неизвестна | Telegram |

Оценка не даётся вовсе, и бот говорит почему, если: пользователь уже был в сети при начале
наблюдения; наблюдение прерывалось; Telegram не дал времени конца; время конца раньше первого
наблюдения «в сети» или позже момента, когда оно получено (расходятся часы или пришло устаревшее
наблюдение). Продление статуса и повтор «в сети» с другим сроком не начинают новый интервал.

## Что не проверено

Пример проверен репетицией и проверкой типов. С настоящим Telegram он не запускался: неизвестно,
по каким пользователям и с какой задержкой приходят обновления статуса, насколько свеж статус
при чтении и какие ограничения частоты действуют на такой опрос.
