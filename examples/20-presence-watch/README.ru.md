# 20 — Бот-наблюдатель за статусом «в сети»

Оператор пишет боту имя пользователя, аккаунт рядом находит этого пользователя и наблюдает то,
что Telegram сообщает о его статусе, а бот пересказывает наблюдения оператору. Бот работает через
Bot API, аккаунт — через MTProto, оба живут в одном `App`, и все обращения к Telegram идут через
Yuigram.

| Файл | Что в нём |
| --- | --- |
| `watch.ts` | Вся логика: команды, модель наблюдения, опрос, уведомления |
| `index.ts` | Запуск с настоящим Telegram |
| `login.ts` | Однократный вход аккаунта, с вопросами в терминале |
| `rehearse.ts` | Репетиция без сети: подставные бот и аккаунт, сценарий статусов |
| `config.ts` | Чтение настроек и открытие клиентов и хранилищ |
| `.env.example` | Все имена настроек с безопасными заглушками |

Наблюдать можно только за теми, кто на это согласен.

## Что умеет бот

Команды принимаются только от оператора и только в его личном чате с ботом. Остальным бот
отвечает, что он закрыт, и к аккаунту не обращается.

| Команда | Действие |
| --- | --- |
| `/start`, `/help` | Список команд |
| `/watch @username` | Найти пользователя и начать наблюдение |
| `/unwatch @username` или `/unwatch id` | Прекратить наблюдение |
| `/list` | Кого наблюдаем и последнее наблюдение по каждому |
| `/status`, `/status @username` | Подробно: что известно, откуда и когда |

Наблюдение привязано к идентификатору пользователя, а не к имени: если имя сменится, наблюдаемый
останется тем же, а `/status` скажет, что имя изменилось. Группы, каналы, боты, несуществующие
имена и сам наблюдающий аккаунт отклоняются с объяснением.

## Установка

Пример использует возможности, которых ещё нет в опубликованном `yuigram@0.1.0`, поэтому
запускается из рабочей копии репозитория:

```bash
pnpm install
pnpm build
```

## Репетиция без сети

```bash
pnpm tsx examples/20-presence-watch/rehearse.ts
```

Не нужны ни токен, ни вход, ни соединение. Бот и аккаунт — тестовые клиенты из `yuigram/testing`,
пользователи выдуманы, статусы идут по сценарию, часы и таймер подставные. Репетиция проверяет,
что сказал бот и о чём спросили аккаунт, и завершается с ошибкой на первом расхождении.

## Настройка для настоящего запуска

Скопируйте `.env.example` в `.env` в этом же каталоге и заполните. Файл `.env` и каталог
состояния Git не отслеживает.

| Имя | Что это | Откуда взять |
| --- | --- | --- |
| `TELEGRAM_ENV` | `production` или `test` — общая среда для бота и аккаунта | Выбираете вы |
| `BOT_TOKEN` | Токен бота | @BotFather той же среды |
| `OPERATOR_ID` | Числовой идентификатор оператора | `login.ts` печатает id аккаунта; бот сообщает любому написавшему его id |
| `API_ID`, `API_HASH` | Учётные данные приложения | [my.telegram.org](https://my.telegram.org), «API development tools» |
| `SERVER_KEYS` | Путь к PEM-файлу с публичными ключами серверов Telegram для выбранной среды | Документация Telegram по MTProto; ключи публичные, файл вы создаёте сами |
| `DC_ID`, `DC_HOST`, `DC_PORT` | Первый адрес датацентра (необязательно) | По умолчанию — датацентр 2 выбранной среды |
| `DATA_DIR` | Каталог состояния (необязательно) | По умолчанию `examples/20-presence-watch/state` |
| `POLL_SECONDS`, `WATCH_LIMIT` | Интервал опроса (не меньше 30 с) и предел наблюдаемых (не больше 20) | По умолчанию 60 и 10 |
| `TIME_ZONE` | Часовой пояс для времени в сообщениях (необязательно) | Например `Europe/Moscow` |

Бот и аккаунт всегда работают в одной среде: её задаёт одна переменная `TELEGRAM_ENV`. Каталог
состояния запоминает среду, для которой создан, и запуск с другой средой отклоняется — боевой бот
и тестовый аккаунт не имеют общих чатов. Для тестовой среды нужны её собственные бот, аккаунт и
ключи.

Токен, `API_HASH` и каталог `state/account` — учётные данные. Их нельзя публиковать, вставлять в
сообщения и журналы.

## Вход аккаунта

```bash
pnpm tsx examples/20-presence-watch/login.ts
```

Команда спрашивает в терминале номер телефона, код от Telegram и, если он есть, пароль
двухэтапной аутентификации (пароль не отображается). Авторизация сохраняется в
`state/account`. После входа команда печатает имя и id аккаунта; при повторном запуске она
ничего не спрашивает. Придумывать строку сессии не нужно.

## Запуск

```bash
pnpm tsx examples/20-presence-watch/index.ts
```

`index.ts` ничего не спрашивает: если аккаунт не вошёл, он сообщает об этом и завершается.
Остановка — `Ctrl+C`: сначала останавливается наблюдение (таймер, обработчики, чтение в пути),
затем клиенты.

## Что где хранится

| Путь | Что в нём |
| --- | --- |
| `state/account/` | Авторизация аккаунта, его датацентры и известные ему пользователи. Это вошедший аккаунт |
| `state/watch/` | Список наблюдаемых, последние наблюдения, открытые интервалы и неотправленные уведомления |
| `state/environment` | Среда, для которой создан каталог |

Чтобы начать заново, остановите пример и удалите `state/watch`. Чтобы выйти из аккаунта,
завершите сеанс в настройках Telegram («Устройства») и удалите `state/account`.

## Как идёт наблюдение

- **Обновления.** Telegram сам решает, о чьих статусах присылать обновления аккаунту, и
  подписаться на произвольного пользователя нельзя. Пришедшее обновление обрабатывается сразу.
- **Опрос.** Раз в `POLL_SECONDS` аккаунт читает всех наблюдаемых одним запросом. Чтения не
  накладываются друг на друга; внеочередное чтение возможно не чаще раза в 30 секунд.
- **Порядок.** Если ответ на чтение пришёл позже более нового обновления, он не отменяет
  обновление: решает следующее чтение.
- **Ограничения Telegram.** При `FLOOD_WAIT` чтение приостанавливается на указанное время, а
  следующие интервалы удлиняются.
- **Уведомления.** Состояние и уведомление записываются вместе, уведомление удаляется из очереди
  только после успешной отправки. После сбоя оно будет отправлено повторно, поэтому доставка —
  «не меньше одного раза»: дубль возможен, потеря — нет, пока отправка не отказала пять раз
  подряд.

## Чего пример не знает и не утверждает

- **Видно только то, что Telegram показывает этому аккаунту.** Если пользователь скрыл время
  захода, бот сообщает «точное время скрыто» и переходов не определяет.
- **Тишина не означает «не в сети».** Истёкший срок статуса «в сети» — повод прочитать ещё раз,
  а не переход.
- **Начало интервала — это момент, когда его заметили.** Telegram не сообщает, когда
  пользователь вошёл. Если начало замечено опросом, длительность даётся границами «не меньше … и
  не больше …».
- **Если пользователь уже был в сети, когда началось наблюдение,** начало неизвестно, и
  длительность такого интервала не называется, даже когда известен конец.
- **Разрыв соединения, перезапуск, отказ чтения и `FLOOD_WAIT`** прерывают интервал: он
  сообщается как прерванный, без длительности. Интервалы через разрыв не склеиваются.
- **Короткие заходы между двумя чтениями** могут остаться незамеченными, если Telegram не
  прислал обновление. Сумма наблюдённых интервалов — не «точное время в сети».
- Время Telegram и местное время наблюдения подписаны по-разному и не смешиваются.

## Что не проверено

Пример проверен репетицией и проверкой типов. С настоящим Telegram он не запускался: неизвестно,
по каким пользователям и с какой задержкой приходят обновления статуса, насколько свеж статус
при чтении и какие ограничения частоты действуют на такой опрос.
