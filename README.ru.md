# Yuigram

**Один TypeScript-фреймворк для ботов Telegram и для аккаунтов Telegram.**

[Документация](docs/ru/README.md) · [Проектирование API](docs/api-design.md) · [Примеры](examples) · [English](README.md)

Bot API 10.3 · слой TL 229 · Node.js 22+ · без runtime-зависимостей

</div>

```ts
import { readFileSync } from 'node:fs'
import { Account, App, Bot, bootstrapAt, serverKeysFromPem } from 'yuigram'
import { f as heard } from 'yuigram/account-filters'

const OWNER = Number(process.env.OWNER_ID)

const bot = Bot.fromToken(process.env.BOT_TOKEN!)
const account = Account.fromSession('./me.session', {
  apiId: Number(process.env.API_ID),
  apiHash: process.env.API_HASH!,
  keys: serverKeysFromPem(readFileSync('./telegram-keys.pem', 'utf8')),
  bootstrap: bootstrapAt({ dc: 2, host: '149.154.167.50', port: 443 }),
})

// Бот — пульт управления: владелец говорит, что отправить от имени аккаунта.
bot.onCommand('say', async (message) => {
  if (message.sender?.id !== OWNER) return

  await account.sendText('@example', message.command.rest)
  await message.reply('Отправлено от имени аккаунта.')
})

// То, что слышит аккаунт, возвращается уведомлением от бота.
account.on('message', heard.incoming.and(heard.chat('user')), async (event) => {
  await bot.api.sendMessage({ chat_id: OWNER, text: `Новое сообщение: ${event.text ?? '(без текста)'}` })
})

const app = new App()
app.add(bot)
app.add(account)

await app.start()
```

Yuigram — фреймворк для программ, которые работают с Telegram как бот, как пользовательский
аккаунт или как оба сразу. `Bot` говорит с Bot API по HTTPS. `Account` говорит по MTProto,
который реализован в этом репозитории, а не взят обёрткой из другой библиотеки. `App` держит
сколько угодно тех и других в одном процессе, и вокруг всех — одни и те же обработчики, фильтры,
middleware, сессии, хранилища и средства тестирования.

## Зачем оба транспорта в одном фреймворке

Бот может только то, что разрешает Bot API. Аккаунт видит то, что видит человек, но с
посторонними должен разговаривать не он. Проекты, которым нужно и то и другое, обычно склеивают
две несвязанные библиотеки: две модели событий, два вида сессий, два способа тестировать.
Yuigram даёт им одну модель приложения:

- **Бот как пульт управления аккаунтом.** Люди пишут боту, а работа, для которой нужен
  аккаунт, — прочитать историю канала, найти пользователя по имени, отправить сообщение от лица
  человека — выполняется через `Account` рядом, в том же процессе и в том же обработчике.
- **Обновления аккаунта как уведомления бота.** То, что слышит аккаунт, отбирается такими же
  фильтрами, как у бота, и доставляется туда, куда бот может писать.
- **Один набор инструментов вокруг обоих.** Общая цепочка middleware, сессии и хранилища,
  диалоги, форматирование, типы ошибок и журнал; `mockBot` и `mockAccount` прогоняют настоящий
  конвейер любого из клиентов, заменяя только сеть.

Транспорты не притворяются одинаковыми. У бота и у аккаунта разные права, разные контексты и
разные способы назвать чат, и типы это показывают: `event.transport` говорит, через какой из них
пришло обновление, а то, что умеет только один, предлагается только там.

## Установка

**Опубликованный пакет — `yuigram@0.1.0`, и это только клиент Bot API.**

```bash
npm install yuigram
```

`Account`, `App` и пример выше находятся в этом репозитории и в npm ещё не вышли. До следующего
выпуска ими пользуются из рабочей копии:

```bash
git clone https://github.com/yuigram/yuigram
cd yuigram
pnpm install && pnpm build
BOT_TOKEN=123456:ABC-DEF pnpm tsx examples/01-basic-bot/index.ts
```

Node.js 22 или новее, только ESM. Что изменилось после `0.1.0` — в
[docs/migration.md](docs/migration.md). Аккаунту нужны идентификатор и хеш приложения с
[my.telegram.org](https://my.telegram.org), опубликованные Telegram серверные ключи и один вход;
по шагам это показано в [examples/03-basic-userbot](examples/03-basic-userbot). Каталог сессии
или строка сессии — **это** вошедший аккаунт: их не должно быть в репозиториях, журналах и
сообщениях.

## Что внутри

- **Два клиента, одна модель** — `Bot`, `Account` и `App`, который держит несколько тех и
  других; у каждого свой жизненный цикл, свои учётные данные и соединения.
- **Типы из схем** — каждый метод Bot API и каждый метод TL сгенерирован и типизирован;
  контекст обработчика — тот, что положен его виду события, и регистрация его сужает.
- **Слой фреймворка** — фильтры, middleware, роутеры, сессии, диалоги, переживающие перезапуск,
  ограничение частоты и плагины — общие для обоих клиентов.
- **Хранилища** — память, файлы, зашифрованные файлы и хранилище браузера встроены; SQLite и
  Redis — отдельными пакетами; для остального — интерфейс из четырёх методов.
- **Сообщения как есть** — форматирование из HTML, Markdown или построителей, богатые сообщения,
  ответы, которые показываются черновиком по мере написания, отправка и скачивание файлов на
  обоих транспортах.
- **Запасной выход** — `bot.api.call` и `account.api` достают всё, что фреймворк ещё не обернул.

## Состояние

- **Основная цель — Node.js 22+.** Bun, Deno, workerd (локально, через Miniflare) и страница в
  Chromium тоже прошли проверки сред выполнения: вызовы Bot API и вебхуки, хранилища, обмен
  ключами аккаунта, зашифрованные вызовы и обновления. В [docs/runtimes.md](docs/runtimes.md)
  сказано, что запускалось, а что выведено.
- **С самим Telegram ничего из этого ещё не запускалось.** Проверки идут на подставных
  транспортах и на стенде-датацентре, говорящем по настоящему протоколу. Вход в аккаунт и вызовы
  живого сервиса не проверены; подготовленная процедура —
  [docs/live-verification.md](docs/live-verification.md).
- **Бюджет холодного импорта в 100 мс надёжно не выполняется** на машине, где он измеряется;
  метод и цифры — в [docs/performance.md](docs/performance.md).
- Что ещё запланировано — в [docs/roadmap.md](docs/roadmap.md).

Аккаунт действует от имени своего владельца. Yuigram — не инструмент для спама и флуда, и
Telegram ограничивает аккаунты, которые так используют.
