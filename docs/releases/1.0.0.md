# Yuigram 1.0.0

The first release with both protocols, and the first with a stable version number. `0.1.0` was
the Bot API client; `1.0.0` adds `Account`, an MTProto client implemented in this repository,
`App` to run bots and accounts together, and a reworked client surface in which each
registration types its handler's context.

Every package is at `1.0.0`. Three are on npm for the first time. The release was prepared
first as `0.2.0`, which was never published; nothing was released between `0.1.0` and `1.0.0`.

| Package | Role | On npm before |
| --- | --- | --- |
| `yuigram` | What applications install; re-exports the rest | `0.1.0` |
| `@yuigram/core` | Dispatch, middleware, sessions, storage, errors, logging | `0.1.0` |
| `@yuigram/bot-api` | The Bot API subsystem | `0.1.0` |
| `@yuigram/mtproto` | The MTProto subsystem | — |
| `@yuigram/sqlite` | SQLite storage | — |
| `@yuigram/redis` | Redis storage | — |

Node.js 22 or newer, ESM only. Bot API 10.3, TL layer 229. No runtime dependencies outside the
`@yuigram` packages.

## Versions

From `1.0.0` on, the packages follow semantic versioning: a change that breaks the public API
comes in a major version. `yuigram`, `@yuigram/core`, `@yuigram/bot-api` and `@yuigram/mtproto`
always share one version; `@yuigram/sqlite` and `@yuigram/redis` start at `1.0.0` with them and
are versioned on their own after it.

## Upgrading from 0.1.0

The client surface changed, mechanically: renamed methods, one construction form
(`Bot.fromToken`), and a context type per event kind instead of one context in which every field
was optional. Nothing was removed without a replacement. [docs/migration.md](../migration.md)
lists every rename and what replaced it.

## What it brings

- **Accounts.** Sign-in by code, two-step password or QR login; a session kept in a directory,
  a store or a string (its own format, or mtcute's version-3 string); typed events; the full
  TL layer as generated methods, plus an untyped call for anything newer; messages, chats,
  members, dialogs and history, files, presence and the rest listed in
  [docs/api-design.md](../api-design.md).
- **One application, several clients.** `App` holds bots and accounts with their own
  credentials, lifecycles and connections, and handlers that work across both narrow on
  `event.transport` where the protocols differ.
- **The Bot API, broader.** Every method a context can address, bound to what the update
  carried; a named registration per event kind; Bot API 10.3.
- **State.** Framework sessions over a three-method store contract with in-memory, file,
  `localStorage`, encrypted, namespaced and tiered stores; `@yuigram/sqlite` and
  `@yuigram/redis`, which also fence an account's storage between processes; `indexedDb()`
  (`yuigram/indexeddb`) for browser pages and workers.
- **Deployment.** Webhook adapters for `node:http`, Express, Fastify and now Koa (`koaWebhook`),
  and a Fetch-shaped one for edge runtimes; an account hosted in a worker (`yuigram/worker`).
- **MTProxy.** `mtproxy()` (`yuigram/mtproxy`) routes every connection of an account through a
  proxy, for all three kinds of secret, fake TLS included, with no fallback to a direct
  connection.
- **Formatting and streaming.** Formatted text, rich messages and streamed answers as entry
  points of their own (`yuigram/markup`, `yuigram/rich`, `yuigram/stream`).

Each optional entry point is loaded only by a program that imports it, and a Bot API bundle
contains no MTProto code — measured at zero bytes on every CI build.

## Known limitations

- **Startup.** Importing `yuigram` takes 105–110 ms on the reference Windows machine, against
  a 100 ms budget. The cost is Node loading 131 files rather than running their code;
  [docs/performance.md](../performance.md) §2.2 has the measurements. An application bundled into
  one file avoids most of it.
- **What has run against Telegram.** Sign-in by code and two-step password, the key exchange
  against the production key, encrypted calls, users and username resolution, pushed presence,
  restarts that reuse the stored authorization, and a bot's polling and commands. Sending,
  editing and deleting from an account, files, rate limits, datacenter migration and the test
  environment are covered by tests against a local stand-in datacenter, not against Telegram.
  [docs/live-verification.md](../live-verification.md) has the record.
- **Incidents seen once and not explained.** In a live run, three transport `404` answers were
  each recovered by discarding the key, and the account now reports which connection, key and
  recovery were involved. One mechanism that produces that answer has since been found and
  fixed — a temporary key's expiry was compared across clocks, so with this machine's clock
  more than a minute behind the server's, a key was presented after the server had dropped it —
  but whether it caused those answers is not established. A Windows `EPERM` on a file-store rename
  lost one write; operations on one file are now ordered and the rename is retried, but what
  held the file was not identified. Neither recurred in a later, shorter run, which does not
  show that the causes are gone.
- **MTProxy.** Checked against a proxy written for the test suite, an independent
  implementation's obfuscation, and OpenSSL's reading of the TLS greeting — not against a
  real MTProxy server, and not through one to Telegram. The greeting is valid TLS but not a
  copy of a browser's, and it uses the local clock. A proxy is reached over TCP, so it is not
  available in browsers or edge workers.
- **IndexedDB.** The store adds no exclusion of its own: one account per origin is kept by the
  Web Locks guard every account takes, and where Web Locks are missing, by nothing.
- **Session strings.** Yuigram reads and writes its own format and mtcute's version-3 string;
  Telethon, Pyrogram, GramJS and MTKruto strings are not read.
- **No independent security review yet.** The cryptography and the protocol checks are tested
  against published vectors and independent implementations, but no third party has reviewed
  them.
- **Not included.** Secret chats.

An account acts as the person who owns it, and Telegram restricts accounts used for flooding
or spam. [docs/mtproto.md](../mtproto.md) opens with what that means.
