# 1.0.0 release checklist

The one list of what stands between the prepared `1.0.0` and its publication. Each item says
what kind of thing it is, because they are settled differently:

- **Defect** — something shown to behave wrongly. Fixed, or shipped as a known issue.
- **Gate** — a check or commitment the project requires that is not met. Met, or waived by the
  owner.
- **Evidence** — behaviour not yet observed where it matters. Gathered, or stated as a limit.
- **Decision** — a choice that belongs to the owner, not to a test.

An item whose cause is unknown stays open, however long it has not recurred.

## Parity, as far as it goes

The capabilities found missing against the two libraries the surface was compared with — an
MTProxy route, an IndexedDB store and a Koa webhook adapter — are now present. That is a
statement about capabilities. It is not a claim of behavioural equivalence with either library:
the method mapping behind the comparison pairs names and asserts each method's success path
against the stand-in datacenter, and does not establish that every option, output and failure
matches.

## Remote CI and the merge

Pushing `feature/mtproto` triggers nothing by itself: `ci.yml` runs on pushes to `master`, on
pull requests, and by hand. A pull request from it into `master` runs five jobs, none of which
uses a secret or writes anything (`permissions: contents: read`). The ruleset on `master`
requires three of them.

| Job | Required | What only it can establish |
| --- | --- | --- |
| Verify | yes | A clean install from the lockfile on Linux; lint, typecheck, invariants, tests; the performance budgets on the runner, the startup gate failing above 120 ms (item 2); declarations; documentation samples; generated code in sync |
| Package | yes | Smoke of the packed packages on Linux |
| Independence | yes | The dependency and licence gates on a fresh install |
| Runtimes | no | Bun 1.4.2 and Deno 2.9.6 from their setup actions, workerd from a fresh Miniflare install |
| Real Redis | no | The Redis 8.10.2 service container, against the store, counter and leases |

The history is kept by merging with a merge commit, once the ruleset allows that method
(item 11): every commit of the branch then reaches `master` unchanged, with one merge commit on
top whose message is checked before it is confirmed — no co-author trailer, no other
attribution. A squash or a rebase would replace the branch's commits with new ones.

Publication stays a separate, manual step: after the merge, running the Release workflow on
`master` publishes what the merged versions say — the changesets are already consumed, so it
opens no version pull request first — and pushes the tags. Merging does not publish.
