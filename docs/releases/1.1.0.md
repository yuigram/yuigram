# Yuigram 1.1.0

Keeps the MTProto subsystem on the layer Telegram's clients speak now: TL layer 232, from 229.
The raw API gains what the layers between added, service messages read the actions they
introduced, and the one method of Yuigram's own that Telegram changed underneath keeps its
signature.

| Package | Version | What changed |
| --- | --- | --- |
| `yuigram` | `1.1.0` | Re-exports the packages below |
| `@yuigram/core` | `1.1.0` | Nothing; it shares one version with the three above and below |
| `@yuigram/bot-api` | `1.1.0` | Documentation links in the generated types |
| `@yuigram/mtproto` | `1.1.0` | TL layer 232 |
| `@yuigram/sqlite` | `1.0.1` | Depends on `@yuigram/core` `1.1.0` |
| `@yuigram/redis` | `1.0.1` | Depends on `@yuigram/core` `1.1.0` |

Node.js 22 or newer, ESM only. Bot API 10.3, TL layer 232. No runtime dependencies outside the
`@yuigram` packages.

## Versions

`1.1.0` is a minor release although Telegram changed five existing parts of the raw MTProto API,
because the raw API — `account.api`, its untyped `account.api.call`, and the TL types — says what
the pinned layer's schema says and follows it in a minor release, each such change listed in the
notes ([docs/codegen.md](../codegen.md) §7). Yuigram's own API and the Bot API surface keep the
rule `1.0.0` set without exception: a change that breaks them comes in a major version.

## Upgrading from 1.0.0

Nothing changes for a program that does not use one of the five parts below through the raw API.

| Raw API, layer 229 | Layer 232 | What to do |
| --- | --- | --- |
| `botVerification.description: string` | `TextWithEntities` | Read `.text`, and `.entities` for its formatting |
| `botVerifierSettings.custom_description: string` | `TextWithEntities` | The same |
| `bots.setCustomVerification({ custom_description: string })` | takes `TextWithEntities` | Pass `{ _: 'textWithEntities', text, entities: [] }` |
| `payments.getStarGiftWithdrawalUrl({ password })` | `{ tmp_password }` | Prove the password to `account.getTmpPassword` first, or call `giftWithdrawalUrl`, which does |
| `inputPasskeyCredentialFirebasePNV` | removed | Telegram removed it; nothing in Yuigram used it |

`giftWithdrawalUrl(gift, password)` takes and returns what it did. It now proves the password to
`account.getTmpPassword` for 60 seconds, the shortest Telegram allows, and sends the temporary
password that returns; the password itself still never travels.

## What it brings

- **Layer 232 in the raw API.** 63 constructors and 46 methods: a TON wallet and TON Connect
  sessions, on-ramp purchases and currency rates, share themes, tokens that let their holder
  write without paying for messages, and username management for bots. They are reached through
  `account.api`; none has a method of Yuigram's own yet.
- **Three service actions.** `gram-transfer`, `wallet-connect-request` and
  `no-paid-messages-token-used`, each read with every value it carries.
- **Documentation links.** The generated Bot API types link to the stable documentation,
  `core.telegram.org/bots/api`, rather than to Telegram's staging copy of it.

In the repository, not in a package: the scheduled drift job now generates the Bot API only from
the stable documentation, reports the staging copy and a TL layer newer than the pin in issues,
and runs every six hours ([docs/codegen.md](../codegen.md) §6). It is what reported layer 232.

## Known limitations

- **Layer 232 against Telegram.** The layer is checked offline: the schema parses, every new
  identifier verifies by recomputation, the generated codecs round-trip, and the test suites run
  against a local stand-in datacenter. It has not been run against Telegram's servers.
- Everything listed for `1.0.0` in [1.0.0.md](1.0.0.md) still applies.
