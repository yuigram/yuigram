# 1.0.0 functional test plan

A plan for someone testing the prepared `1.0.0` from outside the project: how it behaves when
things go wrong, across restarts, with stored sessions and files. The automated suites run
against stand-ins; this is the part that needs a person, a network and real clients.

**This is not a security review.** It looks for wrong behaviour a user would meet. It does not
examine the cryptography or the protocol checks, and a clean result says nothing about them —
that is the independent review [security.md](../security.md) §9 asks for, which has not taken
place.

## Ground rules

- **Only accounts and bots the tester controls.** A secondary account, or Telegram's test
  environment with its `+99966` numbers ([live-verification.md](../live-verification.md) §2),
  and a bot made for the test. Nobody else's chats, and no real personal data: messages and
  files are made up for the test.
- **Session data is a credential.** A session directory, a session string, a bot token and an
  api hash each give control of the account or the bot. Keep them outside the repository, never
  paste them into a report, and delete them when done; end the session from an official client
  afterwards ([live-verification.md](../live-verification.md) §6).
- **Do not provoke Telegram's limits.** Flooding to see a `FLOOD_WAIT` puts the account at risk.
  Record one if it happens; do not go looking for it.
- Redact before reporting: tokens, session strings, codes, passwords, phone numbers.

## Setup

Node 22 or newer. Build and pack from the revision under test (`pnpm install`, `pnpm build`,
`pnpm pack` in each package), or use the examples in place. `tools/live` runs the scripted
checks of [live-verification.md](../live-verification.md) §5; run those first, then the cases
below by hand with examples `01-basic-bot`, `03-basic-userbot`, `04-bot-and-userbot` and
`10-production`.

## Cases

| Area | Do | Expect |
| --- | --- | --- |
| Failures at start | A wrong bot token; a wrong api hash; a malformed or truncated session string; no network | A typed error that names the problem and contains no secret; nothing half-started left running |
| Failures in handlers | A handler that throws; one that never settles | The error reaches `onError`; the client keeps serving other updates |
| Reconnects | Cut the network for 30 seconds, then for 5 minutes, with a bot polling and an account connected; sleep and wake the machine; change networks | Both resume without a restart. Updates sent meanwhile arrive once, in order, after the gap is caught up |
| Restarts | Stop with Ctrl+C and start again; kill the process outright and start again | No new sign-in. Updates resume from where they stopped |
| Two processes | Start a second process on the same session directory | Refused while the first holds it |
| Stored sessions | File, SQLite and Redis stores; the encrypted store with the right and then a wrong passphrase; export a session string and start from it | Each resumes the account; a wrong passphrase is refused, not overwritten |
| Sessions from an earlier build | Start the release on a session directory written by an earlier pre-release build, if one exists | Connects without signing in again. One extra key exchange per datacenter is expected |
| Clock | If possible, set the machine's clock a few minutes behind and then ahead of the true time; run for an hour each way | Connects and stays connected. Report any transport `404` with the diagnostics printed around it |
| Files | Send and download small and large files (over 20 MB from an account), photos and documents, as the bot and as the account; names with spaces and non-Latin characters | Content identical, byte for byte, and the name arrives as sent. A download is written only where the program says |
| Cancellation | Abort a large upload and a large download part-way; press Ctrl+C during sign-in and during a transfer | The operation rejects as cancelled, nothing is left running, and the next operation works |
| Errors from Telegram | Send to a chat that does not exist; edit a message twice with the same text; answer an expired callback query | A Telegram error with its code and description, not a crash |

## Reporting

For each finding: the revision, the operating system and runtime, the steps, what was expected,
what happened, whether it repeats, and the program's output with secrets removed. A finding that
happened once and did not repeat is still worth reporting, marked as such.
