# Клиенты и жизненный цикл

[Оглавление](README.md) · назад: [Быстрый старт](getting-started.md) · дальше:
[События и обработчики](handlers.md)

В Yuigram два вида клиентов и контейнер для них:

| Класс | Транспорт | Чем он является в Telegram |
| --- | --- | --- |
| `Bot` | Bot API поверх HTTPS | бот |
| `Account` | MTProto | пользователь — или бот, вошедший через `signInAsBot` |
| `App` | — | приложение, в котором живут несколько клиентов |

Классы разные, потому что разные их возможности. У `Bot` нет разрешения собеседников по
access hash — Bot API адресует чаты по идентификатору. У `Account` нет повторного использования
`file_id` — это понятие Bot API. Тип клиента сразу говорит, что можно вызвать, и автодополнение
не предлагает методов, которые упадут во время выполнения.

## Бот

```ts
import { Bot, createLogger } from 'yuigram'

const bot = Bot.fromToken(process.env.BOT_TOKEN!, {
  name: 'support',                     // имя в логах и в App
  log: createLogger({ level: 'info' }),
  defaults: { '*': { parse_mode: 'HTML' } },
})
```

Параметры `BotOptions`, которые нужны чаще всего:

| Параметр | Назначение |
| --- | --- |
| `name` | Имя клиента в логах и для `app.client(name)`. |
| `log` | Логгер; по умолчанию консольный на уровне `info`. |
| `defaults` | Значения параметров по умолчанию: `'*'` — для всех методов, принимающих параметр, или по имени метода. |
| `testMode` | Тестовая среда Telegram: запросы идут на `/bot<token>/test/<method>`. |
| `baseUrl`, `local` | Собственный сервер Bot API вместо `api.telegram.org`. |
| `client` | Свой HTTP-транспорт вместо встроенного на `fetch`. |

`new Bot(token, options)` делает то же самое, что `Bot.fromToken`; фабрика — основной путь,
потому что по ней видно, как клиент аутентифицировался.

### Long polling

```ts
await bot.poll({
  concurrency: 16,          // сколько обновлений обрабатывается одновременно
  allowedUpdates: 'auto',   // запросить только те виды, на которые есть обработчики
  dropPending: true,        // пропустить накопившееся до запуска
})
```

Обновления одного чата обрабатываются строго по порядку, разные чаты — параллельно, не больше
`concurrency` одновременно (по умолчанию 16). `concurrency: 1` даёт строго последовательную
обработку. Когда обработчики не успевают, цикл перестаёт забирать новые обновления, так что
очередь не растёт без предела. При временных сбоях polling отступает с нарастающей паузой,
соблюдает `retry_after` и останавливается на ошибках, которые повтор не исправит.

`bot.me` после запуска содержит профиль бота; `bot.identify()` запрашивает его явно.

### Webhook

Webhook не запускается вызовом — он отдаёт обработчик чужому HTTP-серверу:

```ts
import { createServer } from 'node:http'
import { nodeWebhook } from 'yuigram/webhook'

const handler = bot.webhook({ secretToken: process.env.WEBHOOK_SECRET })

createServer(nodeWebhook(handler, { path: '/hook' })).listen(8080)
```

В `yuigram/webhook` есть адаптеры `nodeWebhook`, `expressWebhook`, `fastifyWebhook` и
`webWebhook`; последний принимает `Request` и возвращает `Response` — это то, что ждут
серверы на Fetch API и edge-платформы. Сам адрес вебхука регистрируется вызовом
`bot.api.setWebhook({ url, secret_token })`. Повторно доставленные обновления отбрасываются по
`update_id`.

## Аккаунт

```ts
import { Account, bootstrapAt, memory } from 'yuigram'

const account = Account.fromString(process.env.SESSION!, {
  apiId: Number(process.env.API_ID),
  apiHash: process.env.API_HASH!,
  keys,
  bootstrap: bootstrapAt({ dc: 2, host: '149.154.167.50', port: 443 }),
  storage: memory(),
  name: 'me',
})
```

Три способа создать аккаунт:

| Способ | Где живёт состояние |
| --- | --- |
| `Account.fromSession(каталог, options)` | В каталоге на диске (`file()`); переживает перезапуск. |
| `Account.fromString(строка, options)` | Авторизация приходит строкой; всё, что аккаунт пишет во время работы, — в переданный `storage`. `memory()` — когда ничего не должно пережить процесс. |
| `new Account(options)` | Новый аккаунт в переданном `storage`; затем вход через `signIn`. |

Параметры `AccountOptions`:

| Параметр | Назначение |
| --- | --- |
| `apiId`, `apiHash` | Учётные данные приложения с my.telegram.org. Обязательны. |
| `keys` | Публичные ключи серверов (`serverKeysFromPem`). Нужны, пока для каждого датацентра, к которому обращается аккаунт, не сохранена авторизация. |
| `bootstrap` | Первый адрес (`bootstrapAt({ dc, host, port, testMode? })`). Тестовая или боевая сеть — свойство этого адреса. |
| `storage` | Хранилище состояния аккаунта (кроме `fromSession`, который создаёт его сам). |
| `name` | Имя в логах и для `app.client(name)`; оно же определяет область аккаунта в хранилище (по умолчанию `'account'`). |
| `device` | Что сообщается серверу о клиенте: модель устройства, версия системы и приложения, языки. |
| `log` | Логгер. |
| `takeOverStorage` | Заявить, что предыдущий запуск, оставивший область занятой, завершился, и забрать её. |
| `storageGuard`, `storageLeaseMs` | Как удерживается владение областью хранилища между процессами. |
| `albumWindow` | Сколько ждать следующую часть альбома, прежде чем обработать его целиком (250 мс). |

**Одна область — один аккаунт.** Аккаунт хранит ключи, адреса, собеседников и позицию в потоке
обновлений в своей области хранилища, `accounts:<name>:`. Аккаунты с разными `name` могут делить
одно хранилище; два аккаунта с одним именем — в том числе с именем по умолчанию — попадают в одну
область и перезаписали бы авторизации друг друга. Поэтому второй запуск отклоняется ошибкой
`StorageOwnershipError` — там, где это можно установить:

- в одном процессе — реестром этого процесса;
- в браузере — Web Locks, на все страницы, вкладки и воркеры источника;
- между процессами и машинами — арендой области в `@yuigram/sqlite` и `@yuigram/redis`, которая
  проверяется в одном атомарном шаге с каждой записью.

Над обычным каталогом (`file()`) или другим хранилищем без аренды между процессами действует
только запись о владельце: она отклоняет запуск, начавшийся *после* того, как другой её записал,
но это не блокировка — два процесса, стартовавшие одновременно, запустятся оба. Дайте каждому
аккаунту своё имя; для общего каталога нескольких процессов используйте SQLite или Redis.
Подробности — в [storage.md](../storage.md) §4.

Сохранить сессию строкой — `await account.exportSession()`; формат по умолчанию `'portable'`,
`{ format: 'tl-v3' }` даёт строку версии 3, которую пишет mtcute. При чтении формат указывается
явно: `Account.fromString(строка, { …, format: 'tl-v3' })`. Строки Telethon, Pyrogram, GramJS и
MTKruto — другие форматы, и они не читаются. Переносится только авторизация: список собеседников и
место в потоке обновлений прежней библиотеки не переносятся, и обновления, которые она не успела
получить, не запрашиваются.

### Соединение

`connect()` (или `start()`, что для аккаунта одно и то же) устанавливает соединение и начинает
получать обновления. Состояние соединения видно отдельно от жизненного цикла:

```ts
account.onConnectionStatus((status) => {
  // 'offline' | 'connecting' | 'updating' | 'connected'
  console.log(`соединение: ${status}`)
})
```

`'updating'` означает, что аккаунт догоняет обновления, пропущенные за время разрыва. Если
Telegram сообщает, что аккаунт живёт в другом датацентре, клиент переходит туда сам и
запоминает это, чтобы не возвращаться.

## Приложение

```ts
import { type AnyEventContext, App, file, type MtprotoContext } from 'yuigram'

const app = new App<AnyEventContext | MtprotoContext>({ storage: file('./state') })

app.add(bot)
app.add(account)

app.client('support')   // клиент по имени или undefined
app.clients             // все клиенты в порядке добавления
```

`storage` приложения — для состояния фреймворка: того, что накапливают обработчики и плагины.
Авторизация аккаунта там не хранится и храниться не может — это другой договор с другой
моделью угроз, и аккаунт получает своё хранилище напрямую.

Без аргумента типа `new App()` описывает события клиентов как `BaseContext`: вид, транспорт,
клиент, логгер и исходное обновление. Этого хватает для middleware, которое пишет логи или
считает метрики. Объединение контекстов клиентов в аргументе типа позволяет обработчику
сузить тип по `transport` и читать то, что есть только у одного транспорта.

## Запуск и остановка

| | Бот | Аккаунт | Приложение |
| --- | --- | --- | --- |
| запуск | `poll()`, либо `webhook()` для чужого сервера | `connect()` / `start()` | `start()` — запускает каждый клиент |
| остановка | `stop({ timeout })` | `stop({ timeout })` | `stop({ timeout })` — останавливает каждый |
| состояние | `bot.state` | `account.state`, `account.connectionStatus` | — |

Каждый клиент называет свой механизм запуска, потому что от него зависит, как устроено
развёртывание. Общий глагол `start` есть только у `App` — это единственный объект, который знает,
какой механизм нужен каждому клиенту.

`stop()` не обрывает работу, а дожидается её: приём новых обновлений прекращается сразу,
начатые обработчики получают время до `timeout`, затем закрываются соединения. Возвращаемое
значение говорит, успело ли всё завершиться. Состояние — одно из `'idle'`, `'starting'`,
`'running'`, `'stopping'`, `'failed'`.

```ts
process.once('SIGINT', async () => {
  const drained = await app.stop({ timeout: 10_000 })
  if (!drained) console.error('не все обработчики успели завершиться')
  process.exit(0)
})
```

## Отмена и тайм-ауты вызовов

Вызов Bot API принимает вторым аргументом `{ signal, timeout }`:

```ts
const controller = new AbortController()
setTimeout(() => controller.abort(), 5_000)

await bot.api.sendMessage({ chat_id: 1, text: 'привет' }, { signal: controller.signal })
```

Отмена прерывает HTTP-запрос. Это особенно важно для long polling: запрос висит до минуты, и
остановка, которая не может его отменить, ждала бы весь тайм-аут.

У аккаунта параметры вызова задаются представлением `withParams`:

```ts
const patient = account.withParams({ timeout: 60_000 })
await patient.call({ _: 'help.getConfig' })
```

Здесь `signal` прекращает *ожидание соединения*, но не отзывает запрос, который уже ушёл в
датацентр: в MTProto нет способа забрать отправленный вызов обратно. Это различие транспортов,
и API его не скрывает.

Подробнее: [api-design.md](../api-design.md) §1–3 и §14, [bot-api.md](../bot-api.md),
[mtproto.md](../mtproto.md), [events.md](../events.md) §7.
