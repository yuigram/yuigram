# Спецификация примера: бот-наблюдатель за статусом «в сети»

**Состояние: не реализовано.** Это описание следующего примера (`examples/20-presence-watch`),
а не готового кода. Пример ещё не написан и не запускался; с настоящим Telegram он будет
проверяться отдельно, по [live-verification.md](../live-verification.md).

Пример показывает главное в Yuigram: бот — интерфейс, аккаунт — исполнитель, и оба живут в
одном `App`. Все обращения к Telegram идут только через Yuigram (`Bot`, `Account`, `App`). Других
SDK, обёрток TDLib, парсинга страниц и собственных клиентов протокола в примере нет; от
платформы берутся только конфигурация, часы и файловая система.

## 1. Что делает пример

1. Оператор открывает бота и присылает имя пользователя: `/watch @username`.
2. Аккаунт, работающий рядом, находит этого пользователя и запоминает его постоянный
   идентификатор.
3. Приложение наблюдает то, что Telegram действительно сообщает о статусе этого пользователя.
4. Бот сообщает оператору о замеченных переходах «в сети → не в сети» и обратно и о
   длительности интервалов «в сети», у которых известны обе границы.

Пример ничего не восстанавливает и не обходит: если Telegram скрывает точное время, бот так и
говорит. Наблюдать можно только за теми, кто на это согласен; в репетиции участвуют только
синтетические пользователи.

## 2. Что Telegram сообщает и как это доходит до приложения

**Статус пользователя** в схеме — `UserStatus`, шесть вариантов. Yuigram читает их в
`UserView.presence` (`UserPresence`):

| Вариант схемы | `presence.state` | Что известно |
| --- | --- | --- |
| `userStatusOnline(expires)` | `'online'` | `onlineUntil` — серверное время, до которого статус считается действующим |
| `userStatusOffline(was_online)` | `'offline'` | `lastSeen` — серверное время последнего пребывания в сети |
| `userStatusRecently` | `'recently'` | точного времени нет |
| `userStatusLastWeek` | `'last-week'` | точного времени нет |
| `userStatusLastMonth` | `'last-month'` | точного времени нет |
| `userStatusEmpty` | `'long-ago'` | ничего |
| (бот) | `'bot'` | у ботов статуса нет |

`hiddenByMe: true` означает, что время скрыто потому, что сам наблюдающий аккаунт скрывает
своё, — Telegram отвечает взаимностью.

**Источников два, и они не равны.**

- **Обновление `updateUserStatus`.** Yuigram доставляет его аккаунту событием вида
  `mtproto:user_status`; `event.target` — пользователь (`{ kind: 'user', id }`), сам статус лежит
  в `event.raw`. У обновления нет места в последовательности `pts`, поэтому пропущенное за время
  разрыва не возвращается. Подписаться на статусы произвольного пользователя в протоколе
  нельзя: Telegram сам решает, о ком присылать такие обновления (контакты, недавние
  собеседники), и это поведение не документировано. **Пример не рассчитывает на непрерывный
  поток для любого имени.**
- **Чтение `users.getUsers`.** `account.users([...])` читает всех наблюдаемых одним вызовом и
  возвращает `UserView` с актуальным `presence` — в тех пределах, в которых настройки
  приватности пользователя позволяют этому аккаунту его видеть.

Отсюда схема наблюдения: **редкий ограниченный опрос как основа, обновления как уточнение.**

- Опрос — один вызов `account.users` на всех наблюдаемых, не чаще одного раза в 60 секунд
  (настраивается, нижняя граница 30 секунд), со случайным сдвигом. Наблюдаемых не больше 20.
- Обновление `mtproto:user_status` по наблюдаемому пользователю обрабатывается сразу и
  уточняет картину между опросами.
- Если у статуса «в сети» истёк `onlineUntil`, а нового сообщения нет, это **не** считается
  уходом из сети: делается один внеочередной опрос (не чаще одного на пользователя в 30
  секунд), и вывод делается только из его ответа.
- `FloodError` останавливает опрос на `retryAfter` секунд и удваивает интервал до следующего
  успешного чтения. Повторов чаще расписания нет.

## 3. Команды бота

Команды, которые трогают аккаунт, доступны только оператору: его идентификатор задаётся в
конфигурации (`OPERATOR_ID`), а проверка стоит перед обработчиками — `when(f.sender.id(OPERATOR_ID), …)`
на роутере с этими командами. Всем остальным бот отвечает, что он закрытый, и к аккаунту не
обращается.

| Команда | Что делает |
| --- | --- |
| `/watch @username` | Находит пользователя, начинает наблюдение, отвечает текущим наблюдением |
| `/unwatch @username` | Прекращает наблюдение; открытый интервал закрывается как незавершённый |
| `/list` | Кого наблюдаем, с какого времени, последнее наблюдение по каждому |
| `/status @username` | Текущее наблюдение: что известно, откуда и когда получено |
| `/help` | Команды и ограничения примера |

**Разрешение имени.** `/watch` вызывает `account.user('@username')`. Ответ — `UserView`; в
хранилище записывается `{ kind: 'user', id }` и имя, под которым пользователь был найден.
Дальше пример обращается к пользователю только по идентификатору: имя может смениться, а хеш
доступа аккаунт хранит сам. Отказы различаются: имя не занято (`RpcError` с
`USERNAME_NOT_OCCUPIED`), по имени ничего нельзя назвать (`PeerError`), имя принадлежит каналу
или группе (`account.user` отказывает тем же `PeerError`), это бот (`presence.state === 'bot'` —
наблюдать нечего), пользователь уже наблюдается.

## 4. Модель наблюдения

Каждое наблюдение — запись:

```
{ userId, state, serverTime?, observedAt, source: 'update' | 'poll' }
```

- `serverTime` — время от Telegram: `lastSeen` для «не в сети», `onlineUntil` для «в сети».
- `observedAt` — местное время, когда приложение это узнало. Эти два времени никогда не
  смешиваются и в выводе подписаны по-разному.

**Повторы.** Наблюдение, совпадающее с предыдущим по `state` и `serverTime`, не создаёт
перехода. «В сети» с новым `onlineUntil` — продление, а не новый вход. Одно и то же событие,
пришедшее и обновлением, и опросом, учитывается один раз.

**Интервал «в сети».**

- Начало: первое наблюдение `'online'` после наблюдения другого состояния. Серверного времени
  начала Telegram не даёт, поэтому начало — это `observedAt`, а момент раньше него ограничен
  предыдущим наблюдением: «начало между T₀ и T₁».
- Конец: наблюдение `'offline'`; его `lastSeen` — серверное время конца.
- Интервал **полный**, если между началом и концом не было разрыва наблюдения и `lastSeen` не
  раньше наблюдённого начала. Длительность сообщается как `lastSeen − observedAt начала`, с
  оговоркой о точности: «не меньше» плюс ширина окна между опросами, если начало замечено
  опросом.
- Интервал **неполный**, если: наблюдение началось, когда пользователь уже был в сети; был
  разрыв соединения или перезапуск; `onlineUntil` истёк, а подтверждения нет; после «в сети»
  пришло размытое состояние (`'recently'` и подобные) без `lastSeen`; наблюдение сняли командой.
  У неполного интервала длительность не называется — только известная граница.

**Размытые состояния.** `'recently'`, `'last-week'`, `'last-month'`, `'long-ago'` — это ответ
«точное время скрыто». Наблюдение продолжается, но переходов и длительностей из них не
выводится; бот один раз сообщает, что точные данные недоступны (и отдельно — если причина в
`hiddenByMe`).

**Отсутствие обновлений ничего не значит.** Тишина — не «не в сети».

## 5. Что бот пишет

```
🟢 @sample_user в сети
   замечено: 14:02:11 (местное время, обновление)
   статус действует до: 14:07:05 (время Telegram)

⚪ @sample_user не в сети
   был(а) в сети до: 14:19:40 (время Telegram)
   замечено: 14:19:43 (местное время, обновление)
   в сети: 17 мин 29 с — от замеченного начала до времени Telegram; начало замечено обновлением

⚪ @sample_user не в сети
   был(а) в сети до: 15:31:02 (время Telegram)
   в сети: не меньше 4 мин 10 с и не больше 5 мин 12 с — начало замечено опросом,
   между 15:25:50 и 15:26:52

◻ @sample_user: интервал не завершён
   в сети с (замечено): 16:40:03
   причина: соединение прерывалось с 16:44:10 по 16:51:37 — что было в это время, неизвестно

◽ @sample_user: точное время скрыто («был(а) недавно»)
   наблюдение продолжается, переходы не определяются
```

`/status` показывает последнее наблюдение теми же полями и возраст наблюдения; `/list` — по
строке на пользователя.

## 6. Состояние и перезапуск

Хранилище — `file('./data')`, разделённое через `namespaced`: сессия аккаунта (её ведёт сам
`Account`), список наблюдаемых и по каждому — последнее наблюдение и открытый интервал. Сессия
аккаунта — это вошедший аккаунт: каталог не попадает в репозиторий и в журнал.

- При остановке записывается время остановки; при запуске каждому открытому интервалу
  добавляется разрыв «с T остановки по T запуска», и он становится неполным.
- `account.onConnectionStatus` отмечает разрывы: уход из `'connected'` открывает разрыв,
  возврат закрывает его и вызывает один внеочередной опрос.
- Наблюдение после перезапуска продолжается по сохранённому списку без команд оператора.

## 7. Жизненный цикл

- `App` держит `Bot` и `Account`; `app.start()` поднимает оба, `app.stop({ timeout })`
  останавливает.
- Таймер опроса запускается в `account.observe({ started })` и снимается в `stopping`; текущий
  опрос доводится до конца или отменяется вместе с остановкой.
- Обработчик `SIGINT`/`SIGTERM` вызывает `app.stop` и только потом завершает процесс.
- Ошибки обработчиков идут в `app.onError`; оператору бот сообщает только о том, что касается
  его команды, без внутренних подробностей и без учётных данных.

## 8. Репетиция без сети

Запускается без токена и без входа, на `mockBot` и `mockAccount` из `yuigram/testing`:

- синтетические пользователи с выдуманными идентификаторами и именами;
- ответы на `contacts.resolveUsername` и `users.getUsers` задаются сценарием
  (`harness.on(method, answer)`), обновления статуса подаются через
  `harness.send.update({ _: 'updateUserStatus', … })`;
- часы подставные, так что опрос, истечение `onlineUntil` и разрыв соединения проигрываются
  без ожидания;
- сценарии: полный интервал по обновлениям; интервал, начало которого замечено опросом;
  повтор одного и того же статуса; скрытый статус; истёкший `onlineUntil` без подтверждения;
  перезапуск посреди интервала; `FLOOD_WAIT` на опросе; чужой пользователь пишет боту; имя не
  найдено; имя канала.

Настоящий вход, настоящий токен и наблюдение за настоящим человеком в репетицию не входят.

## 9. Чего для примера не хватает в Yuigram

- **Типизированного чтения статуса из обновления.** `UserView.presence` читает статус
  пользователя целиком, а событие `mtproto:user_status` отдаёт только `event.raw` с голым
  `UserStatus`. Нужен либо `event.presence`, либо экспортируемая функция, читающая `UserStatus`
  в `UserPresence`, — чтобы пример не повторял этот разбор у себя.

Остальное есть: разрешение имени и чтение пользователей (`account.user`, `account.users`),
событие статуса, состояние соединения (`onConnectionStatus`), наблюдатель жизненного цикла
(`observe`), хранилища, фильтры и `when`, `FloodError` с `retryAfter`, тестовые клиенты.

## 10. Что останется проверить на настоящем Telegram

- по каким пользователям и с какой задержкой Telegram присылает `updateUserStatus` аккаунту,
  у которого они не в контактах;
- насколько свеж статус в ответе `users.getUsers` для таких пользователей;
- какие ограничения частоты действуют на такой опрос.

До этой проверки пример утверждает только то, что показывает репетиция: логика наблюдения
верна для тех статусов, которые приложение получило.
